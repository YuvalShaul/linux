# Configuring the network with systemd-networkd (Ubuntu Server / AWS)

**Prerequisite:** [0-linux-networking-basics.md](0-linux-networking-basics.md) — you should already know that netplan is only a translation layer, and how to tell which manager owns your interface.

This is the server-side counterpart of [1-nm-config.md](1-nm-config.md). On a desktop, NetworkManager rules; on **Ubuntu Server** (and on most cloud images, including AWS EC2 Ubuntu AMIs) the default manager is **systemd-networkd**, fed by netplan.

In this lab you will:
1. Verify that your system is actually managed by systemd-networkd.
2. Understand the **two ways** to configure it: netplan YAML (the Ubuntu way) and native `.network` files (the everywhere-else way).
3. Configure a **permanent static IP**, then switch back to **DHCP**.
4. Learn the cloud-specific gotchas (cloud-init, losing SSH).


### Step 1: Verify that systemd-networkd is used
Two checks. First, is the service running (and enabled, so it survives reboot)?
```
$ systemctl status systemd-networkd
● systemd-networkd.service - Network Configuration
     Loaded: loaded (/usr/lib/systemd/system/systemd-networkd.service; enabled; ...)
     Active: active (running) since Thu 2026-08-14 09:12:03 UTC; 1h 2min ago
```
Second — the decisive check — does networkd actually **own your interface**?
```
$ networkctl
IDX LINK   TYPE     OPERATIONAL SETUP
  1 lo     loopback carrier     unmanaged
  2 ens33  ether    routable    configured

2 links listed.
```
`configured` in the SETUP column means networkd owns `ens33`. If it says `unmanaged`, something else (probably NetworkManager) manages it — go back to the checklist in [0-linux-networking-basics.md](0-linux-networking-basics.md).

`networkctl` is to networkd what `nmcli` is to NetworkManager. Get details about one interface with:
```
$ networkctl status ens33
● 2: ens33
             Link File: /usr/lib/systemd/network/99-default.link
          Network File: /run/systemd/network/10-netplan-ens33.network
                 State: routable (configured)
               Address: 192.168.111.128
               Gateway: 192.168.111.2
```
Note the **Network File** line — it tells you exactly which configuration file produced the current state. That is your best debugging tool in this whole lesson.


### Step 2: Understand where the configuration lives
systemd-networkd reads `*.network` files from three directories, in **priority order**:

| Directory | Who puts files there | Priority |
|---|---|---|
| `/etc/systemd/network/` | **you**, the admin | highest |
| `/run/systemd/network/` | generated at runtime — **this is where netplan renders to** | middle |
| `/usr/lib/systemd/network/` | the distro package | lowest |

Files are processed in lexical (alphabetical) order across all three directories, and **the first file whose `[Match]` section matches an interface wins** — later files are ignored for that interface. That's why file names start with numbers like `10-` or `50-`.

On Ubuntu, look at what netplan generated:
```
$ cat /run/systemd/network/10-netplan-ens33.network
[Match]
Name=ens33

[Network]
DHCP=ipv4
```
So the pipeline on Ubuntu Server is:

**`/etc/netplan/*.yaml` → (`netplan generate`) → `/run/systemd/network/*.network` → systemd-networkd → kernel**

This gives you two valid places to make changes:
- **Option A — edit netplan YAML** (recommended on Ubuntu/AWS): keeps everything in one place, and cloud tooling expects it.
- **Option B — write native `.network` files** in `/etc/systemd/network/`: what you'd do on Debian, Arch, or a container image that has no netplan at all.

We'll do both.


### Step 3 (Option A): Static IP via netplan
First, find your interface name, subnet and gateway exactly as in [1-nm-config.md](1-nm-config.md) Step 0 (`ip link`, `ip route`). We'll reuse the same example values: interface `ens33`, subnet `192.168.111.0/24`, gateway `192.168.111.2`.

Look at what's currently in `/etc/netplan/`:
```
$ ls /etc/netplan/
50-cloud-init.yaml
```
On a cloud image that file is **owned by cloud-init** and its header warns you that changes may be overwritten on next boot (see Step 6). The clean approach: leave it alone and add a **new file with a higher number**, which overrides it per-key:
```
$ sudo nano /etc/netplan/60-static.yaml
```
```yaml
network:
  version: 2
  ethernets:
    ens33:
      dhcp4: false
      addresses:
        - 192.168.111.50/24
      routes:
        - to: default
          via: 192.168.111.2
      nameservers:
        addresses: [192.168.111.2, 8.8.8.8]
```
Notes on the format:
- `addresses` must include the **prefix length** (`/24`) — same rule as `ipv4.addresses` in nmcli.
- `routes: - to: default` is the modern syntax; you may see the deprecated `gateway4:` in old guides.
- netplan is picky about permissions: `sudo chmod 600 /etc/netplan/60-static.yaml` (it will warn otherwise).

**Apply it — the safe way.** If you are on SSH (you are, it's a server), a wrong gateway means you lock yourself out. netplan has a built-in safety net:
```
$ sudo netplan try
Do you want to keep these settings?
Press ENTER before the timeout to accept the new configuration
Changes will revert in 120 seconds
```
It applies the config, and **automatically rolls back after 120 seconds unless you confirm**. If your SSH session survives (reconnect to the new IP if it changed!), press ENTER. Once you're confident, plain `sudo netplan apply` does it without the safety net.

Verify, same as always:
```
$ ip addr show ens33
    inet 192.168.111.50/24 ... scope global ens33
$ ip route
default via 192.168.111.2 dev ens33 proto static
$ networkctl status ens33      # Network File should now mention 10-netplan-ens33.network with your values merged in
$ ping -c 2 8.8.8.8 && ping -c 2 google.com
```
Reboot to prove it's permanent — netplan re-renders your YAML on every boot.


### Step 4 (Option B): Static IP with a native .network file
This is what Step 3 actually did under the hood — now do it directly, the way you would on a netplan-less system. Create a file in `/etc/systemd/network/` (remember: highest priority, and its name must sort **before** netplan's `10-netplan-...` to win the match):
```
$ sudo nano /etc/systemd/network/05-static-ens33.network
```
```ini
[Match]
Name=ens33

[Network]
Address=192.168.111.50/24
Gateway=192.168.111.2
DNS=192.168.111.2
DNS=8.8.8.8
```
The three sections you'll use 95% of the time:
- `[Match]` — which interface(s) this file applies to. `Name=` takes globs too (`Name=en*` matches all Ethernet devices — this is how cloud images configure "whatever NIC shows up").
- `[Network]` — the actual configuration: `Address=`, `Gateway=`, `DNS=`, or `DHCP=ipv4` / `DHCP=yes` instead.
- `[Route]` / `[Address]` — optional extra sections when you need more than one route or address with options.

Apply without a full restart:
```
$ sudo networkctl reload              # re-read config files
$ sudo networkctl reconfigure ens33   # re-apply to the interface
```
(Older habit: `sudo systemctl restart systemd-networkd` — works too, but briefly bounces *all* networkd interfaces.)

Verify with `networkctl status ens33` — the **Network File** line should now show `/etc/systemd/network/05-static-ens33.network`, proving your file won the match over netplan's.

**Clean up before moving on** (so the two options don't fight): `sudo rm /etc/systemd/network/05-static-ens33.network && sudo networkctl reload && sudo networkctl reconfigure ens33`.


### Step 5: Back to DHCP
Netplan route: delete your override and re-apply.
```
$ sudo rm /etc/netplan/60-static.yaml
$ sudo netplan apply
$ ip addr show ens33
    inet 192.168.111.128/24 ... scope global dynamic ens33
```
Native route: in your `.network` file, replace the static settings with:
```ini
[Network]
DHCP=ipv4
```
then `sudo networkctl reload && sudo networkctl reconfigure ens33`. The address shows up as `dynamic` again.


### Step 6: The AWS / cloud-init gotchas
Everything above works on an EC2 Ubuntu instance too, but three things are different in the cloud:

**1. `/etc/netplan/50-cloud-init.yaml` is regenerated.** cloud-init writes that file (typically `dhcp4: true` matched on the NIC's MAC) from cloud metadata on first boot, and may rewrite it later. Never edit it directly. Either add your own higher-numbered file (as in Step 3), or tell cloud-init to stop managing the network entirely:
```
$ sudo nano /etc/cloud/cloud.cfg.d/99-disable-network-config.cfg
```
```yaml
network: {config: disabled}
```
After that, `/etc/netplan/` (or `/etc/systemd/network/`) is fully yours.

**2. You usually should NOT set a static IP on EC2.** The private IP of an instance is assigned by AWS at the VPC level and delivered by DHCP; the DHCP lease *is* the source of truth. If you hard-code a different address inside the OS, AWS will still route traffic to the address *it* assigned, and you'll just break connectivity. The correct way to get a fixed address on AWS is on the AWS side (assign a specific private IP to the ENI, or an Elastic IP for public), and leave the OS on DHCP. Static-IP-in-the-OS is for VMware labs, bare metal, and on-prem servers.

**3. One wrong line = locked out.** On a VMware VM you have the console; on EC2 you (mostly) have only SSH. Always use `netplan try`, and know that EC2's serial console / instance screenshot exists for rescue.


### Bonus: DNS lives in systemd-resolved
On networkd systems, DNS is handled by a sibling service, **systemd-resolved** (`/etc/resolv.conf` is just a symlink to its stub). To see which DNS servers are actually in use, per interface:
```
$ resolvectl status
Link 2 (ens33)
    Current DNS Server: 192.168.111.2
           DNS Servers: 192.168.111.2 8.8.8.8
```
The `DNS=` lines in `.network` files (or `nameservers:` in netplan) end up here.


### Useful commands summary
| Command | What it does |
|---|---|
| `networkctl` | List interfaces and who manages them (`configured` = networkd owns it) |
| `networkctl status <if>` | Details + **which config file** produced the current state |
| `networkctl reload` | Re-read `.network` files |
| `networkctl reconfigure <if>` | Re-apply configuration to one interface |
| `netplan try` | Apply netplan YAML **with automatic rollback** — use over SSH |
| `netplan apply` | Apply netplan YAML permanently |
| `netplan get` | Show the merged result of all YAML files |
| `resolvectl status` | Show actual DNS servers per interface |
| `ip addr` / `ip route` | Inspect the current running kernel state |

### nmcli ↔ networkd cheat sheet
| Task | NetworkManager | systemd-networkd |
|---|---|---|
| Who owns what? | `nmcli device status` | `networkctl` |
| Config lives in | `/etc/NetworkManager/system-connections/` | `/etc/systemd/network/` (+ netplan → `/run/systemd/network/`) |
| Change config | `nmcli connection modify` | edit `.network` / netplan YAML |
| Apply now | `nmcli connection up <name>` | `networkctl reload` + `reconfigure` (or `netplan apply`) |
